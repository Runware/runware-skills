# Fal → Runware structural diff checklist

Apply every row below to the pasted Fal call. Don't skip a row just because it seems obviously fine — the point of a checklist is to catch the row that looks obvious and isn't.

| Dimension | Fal | Runware | Typical verdict |
|---|---|---|---|
| Auth header | `Authorization: Key $FAL_KEY` | `Authorization: Bearer <key>` (or payload `authentication` task) | Needs adjustment — different scheme keyword, not just a different key |
| Endpoint | Per-model URL: `https://queue.fal.run/{endpoint_id}` or `https://fal.run/{endpoint_id}` | One fixed URL: `https://api.runware.ai/v1`; model selected via `model` field in body | Needs adjustment — routing logic moves from URL construction to a body field |
| Request envelope | Bare JSON object matching that model's schema | JSON **array** of task objects — always array-wrapped, even for a single task — with `taskType`, `taskUUID`, `model` always present on each | Needs adjustment — the array wrapper is easy to miss on a single-task request, and every task needs a generated `taskUUID`, which Fal has no equivalent of |
| `taskType` value | Not applicable — Fal routes by endpoint URL, not a body field | A fixed constant per model, not always `imageInference` — confirmed exceptions: upscaler models use `taskType: "upscale"`, vectorize models use `"vectorize"`, background-removal models use `"removeBackground"`. Edit/inpaint/erase/etc. models are still `imageInference`. | Needs adjustment — don't default to `imageInference` for every image-shaped model; check `model-map.md`'s Operation column or the model's own `schema.json` |
| Sync call | `fal_client.run()` / plain POST to `fal.run` — blocks until done | `deliveryMethod: "sync"` — only if the target model's own schema lists `sync` as a valid value (many do not, e.g. Kling video is `async`-only) | Needs adjustment, and don't default to it — recommend `async` instead (see next row) even for models that do support `sync`, since holding a connection open is more exposed to timeouts than a poll loop |
| Async call | `submit()` → `request_id` + `status_url` + `response_url`; poll status until `COMPLETED`/`FAILED` | `deliveryMethod: "async"` → ack with `taskUUID`; poll via `{"taskType": "getResponse", "taskUUID": ...}` | Needs adjustment — different poll target and different status vocabulary (`IN_QUEUE`/`IN_PROGRESS`/`COMPLETED` vs. `processing`/`success`/`error`) |
| Webhook payload | `{"request_id", "gateway_request_id", "status": "OK"|"ERROR", "payload": {...}}` | The flat task object itself at the top level (no wrapper) — but note this differs from Runware's own sync/poll response shape, see next row | Needs adjustment — code reading `payload.images[0].url` becomes code reading `imageURL` directly on the top-level webhook body |
| Direct/sync/polled response envelope | Model output is the entire response body | Wrapped: `{"data": [...], "errors": [...]}` — completed tasks in `data[]`, failed ones in a parallel `errors[]`, both keyed by `taskUUID` | Needs adjustment — and note this wrapper only applies to direct responses and polling, *not* to webhook deliveries (see row above), which are flat. Same task, different envelope depending on delivery method. |
| Webhook retry window | Up to ~31 retries over roughly 1 hour, no redirects followed | Exponential backoff capped at 8s per retry, with jitter — reconfirm current max-retry count/window against the live docs rather than trusting either this file or memory | Needs adjustment — don't assume Fal's generous retry window carries over |
| Response field for output | Varies by model: `images[0].url`, `image.url`, `video.url`, or a bare string — inconsistent across Fal's own catalog | Consistent per modality: `data[0].imageURL`, `data[0].videoURL`, `data[0].audioURL`, `data[0].text` (direct/polled responses) or the same field flat at the top level (webhook) | Maps cleanly in spirit, needs adjustment in code — the array indexing doesn't go away, but the key name and structure become predictable instead of per-model, so per-model output-parsing branches can usually be deleted |
| Dimension/size param | Varies per model: `image_size: {width, height}` object, `image_size` enum string (e.g. `"landscape_4_3"`), or `aspect_ratio` string (e.g. `"16:9"`) — model-dependent, not consistent even within Fal | `width` + `height` as plain integers on the task | Needs adjustment — resolve the enum/aspect-ratio back to actual pixel dimensions if the target Runware model expects explicit width/height |
| Error shape (model-level) | `{"detail": [{"loc", "msg", "type", "url", ...}]}` — Pydantic/FastAPI validation style | `{"errors": [{"code", "message", "parameter", "taskType", "taskUUID", "documentation"}]}` | Needs adjustment — any code branching on `detail[].type` or `.loc` needs rewriting against `code`/`parameter` |
| Error shape (request-level) | `{"detail": "...", "error_type": "..."}` | Same as above — Runware doesn't split model- vs. request-level error shapes | Needs adjustment |
| Rate/concurrency limiting | Explicit concurrency ceiling (starts at 2, scales with spend, max 40 self-serve); 429 + `error_type: concurrent_requests_limit` + `X-Fal-needs-retry` header | No published fixed ceiling; queue-based, signaled via 429/503/504 | Needs adjustment — generalize any Fal-specific error-type check to a generic backoff-on-429/5xx |
| Billing / cost | Separate `billing-events` ledger endpoint, queryable after the fact by request ID | `cost` returned inline in the task response (opt in via `includeCost`); aggregate spend also reviewable via the account-management API (`getUsageActivity`, `getDetails`), broken down by day/model/API key, not by individual request | No equivalent for a per-request lookup specifically — delete that code path, read `cost` from the response instead. For spend auditing over time, point to the account-management API rather than assuming nothing exists. |
| Model addressing | Per-model URL slug (e.g. `fal-ai/flux-pro/v1.1`) | AIR identifier (`creator:family@version`, e.g. `bfl:2@1`) in the `model` field | Needs adjustment — look up the AIR via `model-map.md` or the live catalog, don't guess |
| Streaming | Fal's streaming is model/framework-specific (mainly LLM token streaming); check that model's own doc page | SSE via `deliveryMethod: "stream"`, one consistent event format (`delta`, `finishReason`) for text inference | Needs adjustment — different event shape, and only applies on Runware's side to `textInference` |

## Verdict categories, defined

- **Maps cleanly**: the same concept exists on both sides, and the code change is mechanical (rename a field, change a URL). Low risk.
- **Needs adjustment**: the concept exists on both sides but the shape, vocabulary, or semantics differ enough that a straight rename will silently break something. Always give the concrete before/after when using this verdict.
- **No equivalent**: nothing on the other side does this. Say what happens to that code (usually: delete it) rather than leaving it ambiguous.
