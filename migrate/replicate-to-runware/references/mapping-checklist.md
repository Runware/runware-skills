# Replicate → Runware structural diff checklist

Apply every row below to the pasted Replicate call. Don't skip a row just because it seems obviously fine.

| Dimension | Replicate | Runware | Typical verdict |
|---|---|---|---|
| Auth header | `Authorization: Bearer <REPLICATE_API_TOKEN>` | `Authorization: Bearer <key>` | Maps cleanly — same scheme keyword, unlike Fal's `Key`. Only the token value changes. |
| Endpoint (official model) | `POST https://api.replicate.com/v1/models/{owner}/{name}/predictions` | `POST https://api.runware.ai/v1`, model named in body via AIR | Needs adjustment — routing moves from URL path to a body field |
| Endpoint (community model) | `POST https://api.replicate.com/v1/predictions` with a `version` field (model version hash) | Same as above | Needs adjustment — same target either way, but note the source pattern may include a `version` hash that has no Runware equivalent at all (AIR already encodes a version segment, but it isn't the same kind of identifier — don't try to reuse a Replicate version hash as part of an AIR) |
| Request body wrapping | Inputs nested under `{"input": {...}}` | Fields directly on the task object, and the task object itself sits inside a JSON **array** — Runware never accepts a bare top-level object, even for one task | Needs adjustment — mechanical unwrap, plus don't drop the outer array when there's only one task |
| `taskType` value | Not applicable — Replicate routes by endpoint/slug, not a body field | A fixed constant per model, not always `imageInference` — confirmed exceptions: upscaler models use `taskType: "upscale"`, vectorize models use `"vectorize"`, background-removal models use `"removeBackground"`. Edit/inpaint models are still `imageInference`. | Needs adjustment — don't default to `imageInference` for every image-shaped model; check `model-map.md`'s Operation column or the model's own `schema.json` |
| "Sync" request | `Prefer: wait` header — best-effort; may still return `processing` and require a poll | `deliveryMethod: "sync"` — explicit and deterministic where available, but not every model supports it (check the target model's own schema — some are `async`-only) | Needs adjustment — and don't just swap in `sync` as the new default: it's more exposed to timeouts than a poll loop, so prefer `deliveryMethod: "async"` (next row) as the general replacement for `Prefer: wait`, not `sync` |
| Async pattern | Submit → `{id, status, urls: {get, cancel}, output, metrics, error}` → poll `urls.get` until `status` is `succeeded`/`failed`/`canceled` | Submit with `deliveryMethod: "async"` → poll `{"taskType": "getResponse", "taskUUID": ...}` → wrapped `{"data": [...], "errors": [...]}` response | Needs adjustment — different status vocabulary, different envelope, different poll target |
| Response output field | Varies per model: array of URL strings, bare string, or `{url: "..."}` — no consistent shape across Replicate's catalog | Consistent per modality: `data[0].imageURL`, `data[0].videoURL`, etc. (direct/polled response) or flat at the webhook top level | Needs adjustment in code, but usually lets you delete per-model output-parsing branches |
| Errors | `{"detail": "error message"}` on failure, or a `status: "failed"` prediction with an `error` field containing a string — format is looser and less structured than Fal's split error shapes | One consistent shape: `{"errors": [{"code", "message", "parameter", "taskType", "taskUUID", "documentation"}]}` | Needs adjustment |
| Cost / billing | **No pricing or billing data in the API at all.** No billing-events ledger, no inline cost field. Actual cost has to be estimated externally (scraped list price × measured usage) | `cost` returned inline in the task response (`includeCost: true`) | No equivalent for "how do I read Replicate's real cost from the API" — there's nothing to migrate, because there was never anything there. Delete any code trying to poll/scrape for it and just read Runware's `cost` field. |
| Video billing math (if a developer's code estimates Replicate cost) | Must use the **requested output clip duration** (the `duration` input parameter), not `metrics.predict_time` (server render time, unrelated to output length and can be 10–25x larger) | N/A — Runware's `cost` is already correct, no estimation needed | This is a real, previously-encountered bug (see worked example) — flag it explicitly if the developer's code reads `predict_time` for any cost-adjacent purpose |
| Model addressing | `owner/model-name` slug, sometimes with a `version` hash for community models | AIR (`creator:family@version`) | Needs adjustment — look up via `model-map.md` or the live catalog, don't guess |
| Concurrency / rate limits | Replicate enforces account-level concurrency limits (spend-based); a hit monthly spend cap returns HTTP 402 "Monthly spend limit reached" — an account/billing setting, not a request-shape issue. Note: as of July 2025 Replicate no longer lets *new* customers set a monthly spend limit, so this specific 402 is mainly a legacy-account behavior, not something a fresh migration will necessarily hit. | Queue-based, no fixed hard limit, signaled via 429/503/504 | Needs adjustment — a Replicate 402 has no Runware analog; a Runware 429 has no Replicate analog. Don't map these error codes onto each other. |

## Verdict categories, defined

- **Maps cleanly**: the same concept exists on both sides, and the code change is mechanical (rename a field, change a URL). Low risk.
- **Needs adjustment**: the concept exists on both sides but the shape, vocabulary, or semantics differ enough that a straight rename will silently break something. Always give the concrete before/after when using this verdict.
- **No equivalent**: nothing on the other side does this. Say what happens to that code (usually: delete it) rather than leaving it ambiguous.
