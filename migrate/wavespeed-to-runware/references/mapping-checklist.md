# WaveSpeed → Runware structural diff checklist

Apply every row below to the pasted WaveSpeed call. Most of this checklist is confirmed against a real, fully executed call (`wavespeed-ai/flux-dev` → `runware:101@1`, see `references/worked-example.md`). Rows marked **(model-specific, verify)** cover behavior that can vary by model and wasn't directly exercised by that example — check the specific model's own schema, or make a real test call, before relying on them.

| Dimension | WaveSpeed | Runware | Typical verdict |
|---|---|---|---|
| Auth header | `Authorization: Bearer <WAVESPEED_KEY>` | `Authorization: Bearer <key>` | Maps cleanly — same scheme as Runware, unlike Fal's `Key`. Only the token value changes. |
| Endpoint | `POST https://api.wavespeed.ai/api/v3/{model_id}` | `POST https://api.runware.ai/v1`, model named in body via AIR | Needs adjustment — routing moves from URL path to a body field |
| Request body | Bare object matching that model's own schema, fields at top level | Fields directly on the task object, but the task object itself sits inside a JSON **array** — Runware never accepts a bare top-level object, even for one task | Needs adjustment — the array wrapper is easy to miss when a WaveSpeed call was a flat, unwrapped object; the actual field names and formats still need per-model adjustment too |
| `taskType` value | Not applicable — WaveSpeed routes by model ID in the URL, not a body field | A fixed constant per model, not always `imageInference` — confirmed exceptions: upscaler models use `taskType: "upscale"`, vectorize models use `"vectorize"`, background-removal models use `"removeBackground"`. Edit/layered-edit models are still `imageInference`. | Needs adjustment — don't default to `imageInference` for every image-shaped model; check `model-map.md`'s Operation column or the model's own `schema.json` |
| Dimension format | At least one real schema (`flux-dev`) uses `size: "1024*1024"` — an asterisk-delimited string, not an object or separate fields. **(model-specific, verify)** — don't assume this format is universal across WaveSpeed's catalog. | `width` / `height` as separate integers | Needs adjustment — parse the `*`-delimited string, don't assume `x`-delimited or object-shaped |
| Output format naming | Lowercase values (`jpeg`/`png`/`webp`) | Documented as uppercase in the model schema (`JPG`/`PNG`/`WEBP`) — use that casing. The API also accepts lowercase without erroring, but that's undocumented leniency, not the spec. | Maps cleanly with a rename — write the uppercase values (`"JPG"`, not `"jpg"`) rather than relying on the API's leniency |
| Seed convention | At least one real schema defaults `seed` to `-1` as an explicit "random" sentinel. **(model-specific, verify)** — not directly tested here (the confirmed example used an explicit seed). | No sentinel value — confirmed via the live model schema: `seed` is a plain integer with **minimum 0** (so `-1` isn't even a valid value on Runware's side), no default, and the schema states plainly that omitting the field generates a random seed. | Needs adjustment — don't send `-1` (or any WaveSpeed sentinel) through to Runware; drop the field entirely for "random" instead of translating the sentinel value |
| "Sync" hint | Some models expose `enable_sync_mode: boolean`; per its own schema description, `true` can still return a timeout body while the task keeps processing. **(model-specific, verify)** — the confirmed example used the default (`false`). | `deliveryMethod: "sync"` — only valid where the target model's own schema lists it (some Runware models are `async`-only); where it is valid, it's deterministic rather than a best-effort hint like WaveSpeed's `enable_sync_mode` | Needs adjustment, and don't default new code to `sync` even where it's available — prefer `deliveryMethod: "async"`, which every model supports and which avoids holding a connection open under load |
| Base64 output | Some models expose `enable_base64_output: boolean` as an alternative to a CDN URL. **(model-specific, verify)** | `outputType`, an enum with three values: `"URL"` (default), `"base64Data"`, and `"dataURI"` — not a boolean toggle, so `true`/`false` doesn't map directly | Maps cleanly in spirit — set `outputType: "base64Data"` (or `"dataURI"` if you want the `data:` URI prefix included) in place of `enable_base64_output: true`. Confirm the exact field name and values against the target model's own schema, since not every model necessarily exposes all three. |
| Async / submit-poll pattern | Confirmed: submit returns `data.urls.get` directly; polling that URL returns `status` progressing `created` → `processing` → `completed`, output landing in `data.outputs` once done | `deliveryMethod: "async"` + `getResponse` polling, response wrapped `{"data": [...]}`, `errors` appearing only on failure | Needs adjustment — different status vocabulary, different poll-URL mechanics, different envelope |
| Response envelope | Confirmed: `{"code", "message", "data": {...single object...}}` for catalog, pricing, and generation calls alike — no separate top-level `errors` array; failure state lives in `data.status`/`data.error` | `{"data": [...array...]}`, with `errors` appearing only when something fails | Needs adjustment — different shape (object vs. array) and different error-signaling location, not just a different wrapper key name |
| Cost / pricing | A dedicated `POST /api/v3/model/pricing` endpoint (`{model_id, inputs}` → `{data: {unit_price, currency}}`) computes exact cost **before** calling, driven by a per-model formula | `cost` returned inline in the task response (`includeCost: true`) — known only **after** the call | Needs adjustment for timing (pre-flight vs. post-hoc); a pre-flight pricing call itself has no equivalent to migrate — Runware doesn't offer (or need) one the same way |
| Model addressing | WaveSpeed model ID (e.g. `wavespeed-ai/flux-dev`), often already split by operation (text-to-image vs. edit) | AIR (`creator:family@version`) | Needs adjustment — look up via `model-map.md` or the live catalog, matching on operation as well as model family |

## Verdict categories, defined

- **Maps cleanly**: the same concept exists on both sides, and the code change is mechanical. Low risk.
- **Needs adjustment**: the concept exists on both sides but the shape, vocabulary, or semantics differ enough that a straight rename will silently break something. Always give the concrete before/after when using this verdict.
- **No equivalent**: nothing on the other side does this. Say what happens to that code (usually: delete it) rather than leaving it ambiguous.
